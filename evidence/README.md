# evidence/

One directory per run. Discovery, replay and escalation all write through
`src/evidence/writer.py`, so the shape below is the same whichever produced it. That is the
point: a tool or a person that can read one of these can read all of them.

`evidence/*` is gitignored, so everything at the top level is whatever a developer last ran.
**`evidence/curated/` is the deliverable**, and it is tracked. Start there.

## The curated set

Eight runs, in the order they should be read. `INDEX.md` in that directory is the same table
generated by `src/evidence/index.py`. Requirement numbers are the brief's section 3.

| run | brief requirement | exit | result | what it demonstrates |
| --- | --- | --- | --- | --- |
| `01-discovery-real` | 3.1, 3.2 | 0 | success | An LLM drove the real UI with no API and no hardcoded selectors, and the transcript it left is what the recorder compiled into a capability |
| `02-replay-success` | 3.3 | 0 | success | The compiled artifact replays with no model in the decision loop and returns the declared output |
| `03-replay-business-outcome` | 3.3 | 10 | business_outcome | A record that does not exist is an answer, not a crash. This is the run Deliverable 3 asks for by name |
| `04-replay-recovered` | 3.3 | 0 | success | A recoverable condition, an unexpected maintenance page, is dismissed and shows up as `recoveries_applied` on a success rather than as a result kind of its own |
| `05-replay-hard-failure` | 3.3, 3.5 | 40 | failure | A failed load, the app answering 500, stops the run with a typed failure and all four failure files |
| `06-escalation-handoff` | 3.4, 3.6 | 0 | success | The policy stopped an irreversible step for approval, a person took the same live browser and completed it, control came back, and the run checked the page rather than the report |
| `07-replay-permission-denied` | 3.3 | 10 | business_outcome | A restricted member is an answer, not a crash. The first run to confirm the `member_restricted` detect signal fires |
| `08-replay-validation-rejected` | 3.3, 3.5 | 40 | failure | **A defect, recorded as it happened.** The server rejected the deposit, but replay reported a timeout instead of `validation_rejected`. See below |

Runs 02 to 05 and 07 are one capability with different inputs and conditions, so the result
contract in the design rules, section 7 can be read straight off their exit codes: 0, 10 and 40 from one
artifact.

### The six runtime conditions in section 3.3

| condition | run | how replay handles it |
| --- | --- | --- |
| validation error | `08` | **Not handled correctly.** Detected as a failure, not as the declared business outcome |
| record not found | `03` | Business outcome `member_not_found`, exit 10 |
| permission denial | `07` | Business outcome `member_restricted`, exit 10 |
| unexpected dialog | `04` | Recovered by `dismiss_maintenance_interstitial`, exit 0 |
| session timeout | none | **Uncovered.** The app can simulate it, but no outcome, recovery or run exists. Listed in `REPORT.md` Cuts |
| slow or failed load | `05` | A failed load stops with `app_error`, exit 40. A slow load has no curated run; `tests/test_replay.py` arms the six second delay and asserts the run still succeeds |

### 01-discovery-real is preserved as it was recorded

It has **no `meta.json`**, and `INDEX.md` shows its kind as `unknown` for that reason. The run
was produced on 2026-09-12 against `gemini-3.6-flash`, before phase 8 introduced the metadata
file. It has not been regenerated, because regenerating it means spending a real model call to
replace a genuine artifact with a second genuine artifact that differs only in having one more
file. The run itself is the least reproducible thing in this repository and the most worth
keeping exactly as it happened.

It also holds the member id `100001` **unredacted**, in eight places across `result.json`,
`run.jsonl` and `transcript.json`. The other five runs were produced with `--redact` and hold
zero raw occurrences. The difference is real and worth understanding rather than papering over:
at the time of that run there was no capability, so there was no `ParamSpec` marking
`member_id` as `pii`, and the goal sentence handed to the model names the member directly. The
value is a seeded record in a local stand in credit union, so nothing sensitive is exposed. The
lesson it illustrates is the honest one: redaction protects values somebody declared, and
during discovery nobody has declared anything yet. See `DECISIONS.md` 0040.

### 06-escalation-handoff, and what was scripted

The lease moved between two real processes over real HTTP. The operator console ran on its own
port, `POST /take` and `POST /return` were issued as ordinary requests from outside the run,
and the lease file shows `paused` then `human_control` then `resuming` then `running`.

The clicking was scripted. Playwright's sync API binds a page to the thread that created it, so
the confirm has to be issued from the process that owns the browser rather than from anywhere a
person or a second process could reach. `DECISIONS.md` 0035 covers this. What that gives up is
timing realism; what it keeps is that the click went through the raw page and touched no
`LocatorBundle`, no policy gate and no step index, which is what makes it not automation.

`intervention.json` in that directory is the handoff packet as the console saw it, including
the resolution and the captured human actions.

### 08-replay-validation-rejected shows a defect

The input is valid to the schema and invalid to the application. `initial_deposit` is typed
`currency`, and `-50.00` is a currency, so pre-flight lets it through. A value that is not a
number at all, such as `abc`, is refused at pre-flight with exit 40 before a browser opens, so
the schema does not stop a well-typed bad value, and it should not: only the application knows
a deposit must be positive. The server did reject it: `failure/aria.yaml` and `failure/dom.html`
both show "Initial deposit must be greater than zero."

Replay then got it wrong in two separate ways, and fixing either alone would not be enough:

1. The capability detects `validation_rejected` by the text "Correct the highlighted fields",
   which appears nowhere in the application. The outcome was added by hand and never checked
   against the real screen.
2. Step 4 waits for the text "Review Sub-Account Request" before its step is judged. On a
   rejected form that text never appears, the wait runs out after ten seconds, and the run
   stops as a `timeout`. Declared outcomes are only checked after a step's wait succeeds, so
   even a correct detect signal would never have been read.

Nothing was changed to make this run pass. Both fixes are recorded in `DECISIONS.md` 0045.

The same capability also declares `member_restricted`, but that copy cannot fire either. Before
step 0, pre-flight loads the entry screen to compare its fingerprint, sees the "Access Restricted"
title for a restricted member, and stops with `surface_unavailable` as though the application had
changed. Run 07 confirms the signal in the lookup capability only.

## Provenance caveats

**Runs 02 to 08 record an exact commit.** Each was produced from a clean working tree, so the
`git_commit` in its `meta.json` names the code that ran, with no `-dirty` suffix. Each also records
`allow_draft: true`, in `meta.json` and in the engine's own `preflight` event: every one of them
replays a capability that is still a draft, which only happens when `--allow-draft` is passed.
Without the flag the draft gate refuses the run at pre-flight with exit 40.

**02-replay-success names a commit id from before the commit messages were reworded.** Every commit
message in this repository was later rewritten in plainer language. That changed every commit id
but not a single file, so the commit still holds exactly the same code. The evidence was not edited
to match, because evidence is only ever written by a real run. Runs 03 to 06 were produced after
the rewording, as were 07 and 08, and need no translation.

| recorded in 02's meta.json | same commit today |
| --- | --- |
| `7ac0ff9d4312e3e16314132092b42c2682f8a268` | `275433536f048637660d5aca41b641c49a4e6a97` |

**01-discovery-real predates the evidence writer that adds meta.json**, so it has none, and the
index shows its kind as `unknown`. It was preserved rather than regenerated because reproducing it
would cost a model API call, and the key it was produced with has since been revoked. A
reproduction would also not be the same run: the model is not deterministic.

## Directory shape

```
evidence/<run_id>/
    meta.json          what produced this run
    run.jsonl          what happened, one event per line
    result.json        the RunResult the caller received
    transcript.json    discovery only: the full model transcript
    screenshots/
        000.png        in capture order
    failure/           only when the result is not success
        dom.html
        aria.yaml
        screenshot.png
        context.json
```

`<run_id>` is `YYYYMMDD-HHMMSS-xxxx`. It sorts chronologically and the suffix survives two runs
starting in the same second.

## What each file is for

### meta.json

Which code and which allowlist produced this run. Neither is recoverable afterwards, and both
change the meaning of everything else in the directory.

| field | why it is here |
| --- | --- |
| `run_id`, `kind` | which run, and whether it was `discovery` or `replay` |
| `started_at`, `finished_at` | wall clock bounds; the index derives duration from them |
| `capability_id`, `capability_version` | which artifact was replayed, if any |
| `params_redacted` | parameter NAMES and sensitivities. Never values. Built from the capability's declared inputs rather than from the supplied dict, so the code path that could leak one does not exist |
| `model` | which model drove discovery, or absent for replay |
| `allow_draft` | `true` when a draft capability was replayed because `--allow-draft` was passed; `null` for discovery. Without the flag a draft is refused at pre-flight with exit 40, so this field is how a replay of a draft explains itself |
| `git_commit` | the commit that ran, suffixed `-dirty` if the tree was not clean |
| `policy_path`, `policy_sha256` | which allowlist, and exactly which version of it. The path alone is worthless because the file is edited; the hash alone is unreadable because nobody knows which file it belonged to |
| `schema_version` | the shape of this directory, so a reader can tell whether it predates a field |
| `result_kind`, `exit_code` | stamped when the run finishes |

### run.jsonl

One JSON object per line, appended as the run happens: policy blocks, retries, recoveries,
business outcomes, escalations, resumes. Everything passes the Redactor on the serialized
line, so a sensitive value cannot slip through in a field nobody thought about.

### result.json

The `RunResult` union from the design rules, section 7, exactly as the caller received it. Its `kind`
maps to the process exit code: success 0, business_outcome 10, needs_human 20, policy_blocked
30, failure 40.

### transcript.json

Discovery only. Every observation, model turn, tool call and action, in order. This is the
input the recorder compiles into a capability, so a capability in `capabilities/` can always be
traced back to the run that produced it.

### screenshots/

In capture order. Any field bound to a parameter the capability declares `pii` or `secret` is
blacked out at capture time using Playwright's own masking. This is best effort and its limits
are stated in `DECISIONS.md` 0037 and `REPORT.md` section 6.

### failure/

Written whenever the result is not `success`. Section 3.5 asks for at least one signal richer
than the log; there are three, plus the one that explains them.

| file | what it answers |
| --- | --- |
| `dom.html` | what the page actually was |
| `aria.yaml` | what it looked like to the accessibility tree, which is what the system perceives |
| `screenshot.png` | what it looked like to a person |
| `context.json` | why that was not what was expected |

`context.json` is the one worth reading first. It carries the step index, the action, what was
expected, what was observed, and `strategies_tried`: every tier of the locator bundle with the
number of elements it actually matched. A screenshot of a legacy screen cannot tell you that
tier one matched three elements when it should have matched one, and that is usually the whole
explanation.

A **business outcome is not a failure**, and this directory is written for one anyway, because
the screen that produced the outcome is worth keeping. `context.json` carries the real
`result_kind`, so the folder name is never read as the verdict. See `DECISIONS.md` 0036.

## Regenerating each curated run

The target app must be running first:

```bash
make app
```

**01-discovery-real.** Needs `GEMINI_API_KEY` in `.env` and spends a real model call. The
committed run was produced by this command; running it again produces a different run, because
the model is not deterministic.

```bash
python -m src.cli discover \
  --goal "look up member 100001 and read their current savings balance" \
  --target http://localhost:8080 --record
```

**02-replay-success.** Exit 0.

```bash
python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "100001"}' --allow-draft --redact 100001
```

**03-replay-business-outcome.** Exit 10.

```bash
python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "999999"}' --allow-draft --redact 999999
```

**07-replay-permission-denied.** Exit 10. Member 100003 is the seeded restricted record.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "100003"}' --allow-draft --redact 100003
```

**08-replay-validation-rejected.** Exit 40, for the reasons above. Takes about twelve seconds,
most of it the step 4 wait running out.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/open-member-subaccount-1.0.0.json \
  --params '{"member_id":"100001","account_type":"Savings","nickname":"Vacation","initial_deposit":"-50.00"}' \
  --allow-draft --redact 100001
```

**04-replay-recovered** and **05-replay-hard-failure.** These arm a fault first, and the target
app keeps armed faults in the Flask session cookie, so a fault armed from curl belongs to
curl's session and a separate `cua replay` process opens a fresh browser that never sees it.
`scripts/produce_evidence.py` arms it in the same browser context the run then uses, and writes
through the same evidence writer, so the directories are the same shape.

```bash
python scripts/produce_evidence.py fault interstitial     # exit 0, recovery applied
python scripts/produce_evidence.py fault server_error     # exit 40, app_error
```

**06-escalation-handoff.** Three processes. Console first:

```bash
python -m src.cli operator --port 8090 --interventions-dir interventions
```

then the run, which pauses at the irreversible confirm:

```bash
python scripts/produce_evidence.py handoff
```

then take control and hand it back, from a third shell, substituting the id the run printed:

```bash
curl -X POST http://127.0.0.1:8090/i/<intervention-id>/take
curl -X POST -d "outcome=completed_manually&note=opened it by hand" \
  http://127.0.0.1:8090/i/<intervention-id>/return
```

Add `--redact <value>` to any replay for a value the capability does not declare sensitive.
Declared `pii` and `secret` parameters are handled by the schema; `--redact` is for anything
else the caller knows is sensitive.

## Reading the whole directory at once

```bash
python -c "from src.evidence.index import collect, render; print(render(collect('evidence')))"
```

One row per run: run id, kind, result kind, exit code, duration, and the single line that says
what happened. Phase 9 writes this to `evidence/curated/INDEX.md`.
