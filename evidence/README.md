# evidence/

One folder per run. Discovery, replay and handoffs all write through `src/evidence/writer.py`,
so every folder has the same layout, and whatever can read one can read the rest.

`evidence/*` is gitignored, so the top level only holds whatever was run last on this machine.
**`evidence/curated/` holds the sample runs** and is committed. Start there.

## The sample runs

Ten runs, in reading order. `INDEX.md` in that folder is the same table, generated by
`src/evidence/index.py`. Requirement numbers refer to section 3 of the brief.

### The six runtime conditions in section 3.3

| condition | run | what replay does |
| --- | --- | --- |
| validation error | `08` | Business outcome `validation_rejected`, exit 10 |
| record not found | `03` | Business outcome `member_not_found`, exit 10 |
| permission denial | `07` | Business outcome `member_restricted`, exit 10 |
| unexpected dialog | `04`, `10` | A maintenance page is recovered by `dismiss_maintenance_interstitial`, exit 0. A browser `confirm()` is closed with Cancel and the run stops for a person, exit 20. An `alert()` is closed and noted as `dismissed_alert`, which `tests/test_replay.py` covers |
| session timeout | `09` | Recovered by `reauthenticate_after_session_expiry`, which starts the flow again from the first page, exit 0 |
| slow or failed load | `05` | A failed load stops with `app_error`, exit 40. There is no sample run for a slow load; `tests/test_replay.py` turns on the six second delay and checks the run still succeeds |

### 01-discovery-real is kept exactly as recorded

The folder also holds `lookup-member-savings-balance-1.0.0.json`, the capability compiled from
this run's transcript by `record`. It is byte for byte the same as the copy in `capabilities/`.
The replay runs use version 1.2.0, which has the same steps, outputs and success check, plus
the outcomes and recovery added by hand (see `DECISIONS.md` 0027).

It has **no `meta.json`**, which is why `INDEX.md` shows its kind as `unknown`. It was recorded
on 2026-09-12 with `gemini-3.6-flash`, before the evidence writer started adding that file. I
have not re-run it, because that costs a model call and gives back a different run, since the
model is not deterministic. Of everything in the repo it is the hardest to reproduce, so it stays
as it was.

It also contains the member id `100001` **unredacted**, in eight places across `result.json`,
`run.jsonl` and `transcript.json`. The later runs were made with redaction on and contain none.
The reason is that during discovery there was no capability yet, so nothing marked `member_id`
as `pii`, and the goal sentence given to the model names the member. The id belongs to a made-up
record in the local test app, so nothing real is exposed. It does show a real limit: redaction
only protects values someone has marked, and during discovery nothing is marked yet. See
`DECISIONS.md` 0040.

### 06-escalation-handoff, and what was scripted

The lease really did move between two processes over HTTP. The operator page ran on its own
port, `POST /take` and `POST /return` were sent from outside the run, and the lease file went
from `paused` to `human_control` to `resuming` to `running`.

The click itself was scripted. Playwright's sync API ties a page to the thread that created it,
so the Confirm click has to come from the process that owns the browser. `DECISIONS.md` 0035 has
the details. That loses realistic timing. What it keeps is that the click went straight to the
page, without a `LocatorBundle`, the policy check or a step index, so it was not automation.

`intervention.json` in that folder is the handoff request as the operator page saw it, including
how it was resolved and what the person did.

### 08-replay-validation-rejected, and the bugs it found

The input passes the schema but not the app. `initial_deposit` is typed `currency`, and `-50.00`
is a valid currency, so the checks before the run let it through. Something that is not a number
at all, like `abc`, is refused before a browser opens, with exit 40. Only the app knows a deposit
has to be positive, and `failure/aria.yaml` shows it saying "Initial deposit must be greater than
zero."

The first time I produced this run it came back as a `timeout` failure, exit 40, for two
reasons. Capability 1.0.0 looked for the text "Correct the highlighted fields", which the app
never shows. And when a step's wait ran out, here step 4 waiting for the review page, the run
reported a timeout before checking the expected outcomes. Both are fixed: 1.1.0 looks for the
real field errors, and a wait that runs out now checks outcomes first, which is the
`wait_timed_out_on_outcome` line in `run.jsonl`. The run here is the new one against 1.1.0.
`DECISIONS.md` 0045 has the details, including a third bug found the same way: the check before
the run used to treat a restricted member's page as the app having changed. That is fixed too,
so `member_restricted` works in the sub-account capability as well.

## Folder layout

```
evidence/<run_id>/
    meta.json          what produced this run
    run.jsonl          what happened, one event per line
    result.json        the RunResult the caller received
    transcript.json    discovery only: the full model transcript
    screenshots/
        000.png        in capture order
    failure/           only when the result is not success
        dom.html
        aria.yaml
        screenshot.png
        context.json
```

`<run_id>` is `YYYYMMDD-HHMMSS-xxxx`. It sorts by time, and the suffix keeps two runs that start
in the same second apart.

## What each file is for

### meta.json

Which code and which allowlist produced the run. You cannot work either out afterwards, and both
affect how to read everything else in the folder.

| field | why it is there |
| --- | --- |
| `run_id`, `kind` | which run, and whether it was `discovery` or `replay` |
| `started_at`, `finished_at` | start and end time; the index works out duration from them |
| `capability_id`, `capability_version` | which capability was replayed, if any |
| `params_redacted` | parameter names and sensitivities, never values. Built from the capability's declared inputs, not from the values passed in, so there is no code path that could write a value |
| `model` | which model ran discovery, empty for replay |
| `allow_draft` | `true` when a draft was replayed with `--allow-draft`, `null` for discovery. Without the flag a draft is refused, so this is how a draft replay explains itself |
| `git_commit` | the commit that ran, with `-dirty` added if the tree had changes |
| `policy_path`, `policy_sha256` | which allowlist file and which version of it. The path alone is not enough because the file gets edited, and the hash alone does not say which file it was |
| `schema_version` | the layout version of this folder, so a reader can tell if a field is missing because it is older |
| `result_kind`, `exit_code` | filled in when the run finishes |

### run.jsonl

One JSON object per line, written as the run goes: policy blocks, retries, recoveries, business
outcomes, handoffs, resumes. Each line goes through the redactor after it is serialized, so a
sensitive value cannot slip out through a field nobody thought of.

### result.json

The result exactly as the caller got it. Its `kind` matches the exit code: success 0,
business_outcome 10, needs_human 20, policy_blocked 30, failure 40.

### transcript.json

Discovery only. Every observation, model turn, tool call and action, in order. The recorder
compiles this into a capability, so every file in `capabilities/` can be traced back to the run
it came from.

### screenshots/

In capture order. Any field filled from a parameter marked `pii` or `secret` is blacked out
when the screenshot is taken, using Playwright's masking. This does not catch everything; see
`DECISIONS.md` 0037 and the Safety section of `REPORT.md`.

### failure/

Written whenever the result is not `success`. Section 3.5 asks for at least one thing more
useful than the log. There are three, plus a file that explains them.

| file | what it tells you |
| --- | --- |
| `dom.html` | what the page really was |
| `aria.yaml` | what the accessibility tree showed, which is what the run reads |
| `screenshot.png` | what a person would have seen |
| `context.json` | why that was not what the run expected |

Read `context.json` first. It has the step number, the action, what was expected, what was
seen, and `strategies_tried`: every locator tier with how many elements it matched. A screenshot
of an old screen cannot tell you that tier one matched three elements instead of one, and that
is often the whole story.

A **business outcome is not a failure**, but this folder is written for one anyway, because the
screen that gave the answer is worth keeping. `context.json` holds the real `result_kind`, so
nobody mistakes the folder name for the verdict. See `DECISIONS.md` 0036.

## Producing each sample run again

Start the target app first:

```bash
make app
```

**01-discovery-real.** Needs `GEMINI_API_KEY` in `.env` and uses a real model call. This is the
command that made it. Running it again gives a different run.

```bash
.venv/bin/python -m src.cli discover \
  --goal "look up member 100001 and read their current savings balance" \
  --target http://localhost:8080 --record
```

The capability saved in that folder comes from compiling the committed transcript, which needs
no key:

```bash
.venv/bin/python -m src.cli record \
  --transcript evidence/curated/01-discovery-real/transcript.json \
  --out evidence/curated/01-discovery-real/
```

**02-replay-success.** Exit 0.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "100001"}' --allow-draft --redact 100001
```

**03-replay-business-outcome.** Exit 10.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "999999"}' --allow-draft --redact 999999
```

**07-replay-permission-denied.** Exit 10. Member 100003 is the restricted one.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/lookup-member-savings-balance-1.2.0.json \
  --params '{"member_id": "100003"}' --allow-draft --redact 100003
```

**08-replay-validation-rejected.** Exit 10. Takes about twelve seconds, mostly step 4 waiting for
a review page that never shows up.

```bash
.venv/bin/python -m src.cli replay \
  --capability capabilities/open-member-subaccount-1.1.0.json \
  --params '{"member_id":"100001","account_type":"Savings","nickname":"Vacation","initial_deposit":"-50.00"}' \
  --allow-draft --redact 100001
```

**09-replay-session-expired.** Exit 0. Turns on the session expired fault, then replays lookup
1.3.0, which has the restart rule.

```bash
.venv/bin/python scripts/produce_evidence.py fault session_expired \
  --capability capabilities/lookup-member-savings-balance-1.3.0.json
```

The fault fires on the first page, so the restart happens before the run has done anything. That
is enough to show the expiry being noticed and handled. An expiry later in the flow goes the same
way. `tests/test_replay_session.py` also covers the case the rule has to refuse: an expiry after
an irreversible step, which asks for a person instead of starting over.

**10-replay-unexpected-dialog.** Exit 20. Turns on the confirm dialog fault, then replays lookup
1.2.0. The `dialog` and `needs_human` lines in `run.jsonl` say what the pop-up asked and why the
run stopped.

```bash
.venv/bin/python scripts/produce_evidence.py fault confirm_dialog
```

**04-replay-recovered** and **05-replay-hard-failure.** These need a fault turned on first. The
app keeps faults in the Flask session cookie, so a fault turned on with curl belongs to curl's
session, and a separate replay opens a new browser that never sees it.
`scripts/produce_evidence.py` turns the fault on in the same browser the run then uses, and
writes through the same evidence writer, so the folders look the same.

```bash
.venv/bin/python scripts/produce_evidence.py fault interstitial     # exit 0, recovery applied
.venv/bin/python scripts/produce_evidence.py fault server_error     # exit 40, app_error
```

**06-escalation-handoff.** Three processes. The operator page first:

```bash
.venv/bin/python -m src.cli operator --port 8090 --interventions-dir interventions
```

then the run, which pauses at the irreversible Confirm:

```bash
.venv/bin/python scripts/produce_evidence.py handoff
```

then take control and give it back from a third terminal, using the id the run printed:

```bash
curl -X POST http://127.0.0.1:8090/i/<intervention-id>/take
curl -X POST -d "outcome=completed_manually&note=opened it by hand" \
  http://127.0.0.1:8090/i/<intervention-id>/return
```

Add `--redact <value>` to any replay to hide a value the capability does not mark as sensitive.
Parameters marked `pii` or `secret` are already hidden.

## Summarising a folder of runs

```bash
.venv/bin/python -c "from src.evidence.index import collect, render; print(render(collect('evidence')))"
```

One row per run: folder name, kind, result, exit code, duration, and a one-line summary.
`evidence/curated/INDEX.md` is the same table for the sample runs, rebuilt with:

```bash
.venv/bin/python -c "from src.evidence.index import write_index; write_index('evidence/curated', 'evidence/curated/INDEX.md')"
```
